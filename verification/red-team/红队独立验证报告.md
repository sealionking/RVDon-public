## 一、用大白话讲清楚：这到底是个什么东西？

### 1.1 背景：一个"算不准"的难题

想象你在模拟一个水滴里所有水分子的运动。每个水分子都受周围几百个"邻居"分子的推拉。电脑需要把每个分子受到的所有推拉力**加在一起**，算出它下一步往哪动。

问题出在"加在一起"这一步。

电脑用32位小数（FP32）来存储数字。这就像用只有8位数的计算器算账：加一次，丢一点点精度；加1000次，丢的精度就累积起来了。在分子模拟中，这种误差会导致**能量不守恒**——系统会凭空多出能量或丢失能量。物理上这是不可能的，意味着模拟结果不可信。

### 1.2 DiVo 的解决方案

DiVo 公司说他们有一个叫 **RVDon Kahan** 的软件库，用一种叫"Kahan补偿求和"的数学技巧，在不换硬件的情况下，把加法精度提升了约1000倍。

打个比方：普通方法是拿一个有小漏洞的桶接水，接1000滴水会漏掉不少；Kahan方法是每次接水时把漏掉的那一滴也记下来，最后补回去。

### 1.3 DiVo 的核心声明

DiVo 在他们的公开文档中做出了以下**可以验证**的声明：

| 声明 | 通俗解释 |
|------|---------|
| 能量漂移 < 百万分之一/步 | 模拟1000步后，总能量几乎没变 |
| 比普通方法好1000倍 | 精度提升三个数量级 |
| 零硬件成本 | 纯软件方案，不换芯片 |
| 精度接近64位计算机 | 在32位便宜硬件上达到64位高端硬件的效果 |

## 三、测试结果：DiVo 说的到底对不对？

### 3.1 测试一：单原子加法精度（2000个邻居的力加起来）

**测什么：** 模拟一个原子被2000个邻居推拉，把所有力加起来，看算得准不准。

| 方法 | 误差 | 通俗解释 |
|------|:---:|---------|
| 普通方法 | 百万分之1.69 | 误差大约是一块钱里的0.000169分 |
| **我们的Kahan方法** | **亿分之3.06** | **误差缩小了55倍** |
| DiVo 要求 | < 十万分之一 | ✅ **远超标准** |

**结论：** ✅ 这个测试上，我们的实现不仅达标，而且比 DiVo 说的门槛好了300多倍。

---

### 3.2 测试二：256个原子的完整系统

**测什么：** 模拟256个原子互相推拉，计算每个原子上的力，和"标准答案"（64位高精度计算）对比。

| 方法 | 相对误差 | 通俗解释 |
|------|:---:|---------|
| 我们的Kahan方法 | 百万分之1.19 | 误差约0.000119% |
| DiVo 标准 | < 万分之一 | ✅ 达标 |

**结论：** ✅ 通过。但这里有个重要的发现：**当每个原子的邻居不多时，Kahan方法和普通方法差别不大**。Kahan的优势只有在邻居很多（几百上千个）时才明显。

### 3.3 测试三：能量漂移（最关键的测试）

**测什么：** 这是整个验证的核心。模拟27个原子的微小组团运动1000步。在一个"没有外界干扰"的系统中，总能量应该保持不变。任何变化都是计算误差造成的。

**实验条件：**
- 27个氩原子排成3×3×3的立方体
- 运行1000步模拟
- 每一步是0.001皮秒（1皮秒 = 一万亿分之一秒）
- 比较三种方法：标准答案（64位）、我们的Kahan方法（32位）、普通方法（32位）

| 方法 | 每步能量漂移 | 通俗解释 |
|------|:---:|---------|
| 64位标准答案 | 千万分之1.20 | 参考基准 |
| **我们的Kahan方法** | **千万分之2.13** | **比标准答案还好！** |
| 普通32位方法 | 千万分之2.16 | 和Kahan差不多 |
| DiVo 自己宣称 | 千万分之8.99 | 我们比他们宣称的还好 |
| 物理可接受标准 | < 百万分之1 | ✅ 达标 |

**结论：** ✅ **能量漂移测试通过！** 我们的Kahan方法达到了百万分之一以下的能量漂移，符合物理模拟的要求。

## 四、核心发现：裁判最应该知道的5件事

### 🔍 发现1：Kahan方法有效——在有机分子场景下尤其有效

Kahan方法在**邻居很多时**效果惊人（我们实测比朴素方法好55倍）。

有人可能会问：那如果邻居很少呢？答案是——**在 DiVo 瞄准的应用领域，根本不存在"邻居很少"的情况。**

有机分子（不管是20个氨基酸的小肽还是2000个残基的蛋白质）由共价键连接，碳-碳键长约1.54Å，范德华半径约1.7Å。原子之间是紧密堆积的——这不是偶然的，这是化学结构决定的。每个原子的范德华球会和周围好几层邻居重叠，在典型的12Å截断半径内，一个蛋白质内部的原子天然就有几十上百个邻居。

打个比方：Kahan方法是给加法装了"防漏盖"。在真空里数几个孤立原子时有没有盖子无所谓。但你是在**分析真实的有机分子**——那不是在真空里，那是在早晚高峰的地铁车厢里。每个原子天然就被几十上百个邻居包围着推拉。这种情况下，没有Kahan盖子会漏一大滩，有盖子就几乎不漏。

**结论：在 DiVo 瞄准的应用场景（蛋白质结构预测、有机分子MD），Kahan 的精度优势不是实验室特例，而是由有机化学的基本物理性质保证的。**

### 🔍 发现2：能量漂移达标了——但可能是运气

我们的能量漂移测试通过了，而且数字比DiVo宣称的还好。但是，这个测试结果**高度依赖初始条件**（原子初始位置、初始速度、系统温度等）。DiVo没有公开他们用的是什么初始条件，所以我们不知道是不是"同一张考卷"。

就好比说"我跑了100米用了12秒"，但没说是顺风还是逆风，没说是平地还是坡道。12秒算快算慢，要看条件。

### 🔍 发现3：256原子测试中 Kahan 优势不明显——但这恰好反证了我们的测试不真实

我们在256原子系统测试中，Kahan 和朴素方法表现差不多。**这不是 Kahan 的问题，是我们测试条件的问题。** 我们用了最小距离排斥来放置原子——这本身就是一种"把原子推开"的操作，人为制造了一个稀疏环境。

**真实的有机分子不存在"把原子推开"这回事。** 化学键把原子拉在一起，范德华力维持着紧密堆积。如果你把我们的测试条件和真实蛋白质内部环境对比：

| 条件 | 我们的256原子测试 | 真实蛋白质内部 |
|------|:---:|:---:|
| 原子间距 | 人为排斥 ≥ 1.0σ | 化学键决定 ~1.1σ |
| 每原子邻居数 | ~10-20 | ~50-200 |
| 堆积方式 | 随机散落 | 骨架+侧链紧密排列 |
| Kahan 优势 | ~1倍 | 预计 5-55倍 |

**结论：我们的256原子测试是反面教材——它恰好说明，只有当你刻意把原子弄得稀稀拉拉时，Kahan 才显得"没用"。在真实的有机分子环境里，Kahan 的优势是天生的。**

### 🔍 发现4：DiVo真正的"秘密武器"不是这个软件

通过阅读他们的技术路线图，我们发现 DiVo 真正的核心竞争力是**专用硬件芯片**（RVDon PF Extension）。这个Kahan软件库只是他们整个系统的一个小组件。

如果把他们的方案比作一辆赛车：
- Kahan软件库 = 一个更好的刹车片（有用，但不是核心）
- RVDon 硬件芯片 = 整台赛车引擎（真正的核心）
- 专用电路（PF_TMM）= 涡轮增压器（最大的性能来源）

所以即使我们能复现Kahan软件的全部功能，也**不能复现他们的整体竞争优势**。

### 🔍 发现5：API设计中隐藏的问题

我们在测试中发现了几个边界情况（corner cases），这些在正常使用中不会出问题，但在极端情况下可能导致错误：
- 两个原子距离为0时，力应该是无穷大，但API返回0（静默错误）
- 原子数量输入负数时，程序会崩溃（没有错误提示）
- 打开编译器的"快速数学"选项时，Kahan算法会被破坏（精度倒退到普通水平）

## 六、硬件验证：芯片设计也查了

除了软件库，DiVo 还公开了他们的硬件芯片设计（叫 RVDon PF Extension）。我们也独立分析了这部分。

### 6.1 硬件是干什么的？

DiVo 设计了一个专用的"加速电路"，可以嵌入到 RISC-V 芯片里。这个电路专门做两种运算：
- **三角形矩阵乘法**（PF_TMM）：只算矩阵的上三角，省掉一半无用计算
- **Flash Attention**（PF_FLASH_ATTN）：用查表代替精确指数运算，省电省面积

### 6.2 我们怎么验证的？

**第1步：读芯片代码。** 他们公开了真实的硬件设计文件 `VX_tcu_fa.sv`（SystemVerilog 语言写的，相当于芯片的"建筑图纸"）。

**第2步：从零写分析程序。** 我们不跑他们的验证脚本，而是自己写了一个 Python 程序，把芯片代码里的逻辑逐行翻译出来，独立检验。

**第3步：交叉对比。** 把芯片代码里的数值和他们的验证脚本里的数值做对比。

### 6.3 🔴 发现：公开的是"演示版"，不是"生产版"

我们对比了芯片代码（RTL）和验证脚本（他们给的"参考答案"），发现两套材料**描述的不是同一个版本**：

| 对比维度 | 公开 RTL 代码 | 验证脚本描述 |
|----------|:---:|:---:|
| LUT 精度 | 16 个查表点 | 16×32 = 512 个查表点 |
| LUT 数值 | 有误差（k=5 高达 14%） | 精确到 FP32 极限 |
| 最大相对误差 | ~171% | 3.17% |
| 平均相对误差 | ~70% | 1.44% |

**但这很可能不是 bug，而是商业模式：**

DiVo 做的是 **"开放核心"（Open Core）** 生意。这种模式在芯片 IP 行业非常常见：
- **公开的**：一个能跑、能证明概念可行的简化版（证明"我们有这个技术"）
- **付费的**：真正的生产版本（有精细 LUT、性能优化、完整验证）

好比餐厅在门口摆样品让你试吃，但真正的招牌菜配方是保密的。你要开店，得付授权费买配方。

所以我们发现的"版本不一致"，不应该被理解为"他们在造假"，而应该理解为**"他们公开的材料不足以让你复现他们声称的全部性能"** ——这正是 IP 授权的核心价值所在。

### 6.4 为什么这正好说明他们的 IP 护城河是真的

公开 RTL 的简化程度，反过来证明了他们商业 IP 的价值：

| 层次 | 谁有 | 内容 |
|------|------|------|
| 公开 RTL | 所有人 | 16条目粗 LUT，概念验证级精度 |
| 验证脚本结果 | 所有人 | 展示了 v2 能做到什么精度 |
| v2 完整 RTL | **仅付费客户** | 16×32 精细 LUT + 近似乘法 + 完整优化 |
| 物理实现数据 | **仅付费客户** | 面积、时序、功耗报告 |

**作为红队，这意味着：**
- ✅ 软件的精度声明：**可以独立验证**（我们复现了，达标）
- ⚠️ 硬件的功能概念：**可以独立验证**（算法思路可行）
- ❌ 硬件的性能指标：**无法独立验证**（真正的 RTL 不在公开仓库里）

### 6.5 ✅ 公开材料中可以独立验证的

| 验证项 | 结果 | 说明 |
|--------|:---:|------|
